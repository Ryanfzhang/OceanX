## 4. 审核：存在明确的内核失活等待缺陷

审核代码 `codeexec_9b137beb022a4dd7856ff4b4a0e3282d` 自 **11:11:43** 起一直 running，取消前约 54 分钟。12:01 左右进程检查能看到两位作者的内核，但没有审核者内核。不能把这段等待记成 54 分钟 Python 计算。

`src/oceanx/kernels.py:135–154` 的 collect 循环等待 `get_iopub_msg()`，只有收到对应请求的 `idle` 才结束；执行中没有检查 kernel 是否仍存活。执行前的 is_alive 检查不能覆盖执行中退出。当 wall_time_seconds 为 0，外层 timeout 为 None，内核死亡后可能永久等待。这是执行生命周期缺陷，与科学预算应宽或窄是两回事。

## 5. 后台仍在制造重复内容，抵消上下文瘦身

三处代码连起来说明原因：

- `expert_execution.py:1428` 扫描固定 outputs 目录中全部文件，作为每次执行的 output_files。
- `tools.py:578` 将整个累计 output_files 以绝对路径返回给模型；stdout/stderr 已有截断，但文件清单未变成当次增量。
- `expert_execution.py:383–422` 保存报告时遍历每次执行的输出快照，以不同 run 目录再次列出历史文件。

实测一次执行最多列 153 个文件。统计报告正文及开头约 28,151 字符，整个文件却为 **4,799,635 字节、18,615 行**，其中 **18,246 条 Saved files 链接**。这些不代表 18,246 个独立科学发现，而是逐执行快照的重复登记。

审核归档历史确实先读报告三次，并列目录两次。不能声称审核完整读入 4.8 MB；它只读了部分。但后台扩大交接面、迫使模型再找有效内容，是直接可见的问题。把大输出落盘之后仍反复返回历史清单，并没有真正解决重复信息。

摘要修复部分有效：不再像旧测试几乎所有摘要都 length。此次物理 25 次 stop/2 次 length/1 次 failed，统计 12 次 stop/1 次 length，审核 1 次 stop；两次早期 length 后续可见扩大输出上限的 stop 修复。但摘要调用本身累计约 14.6 分钟跨角色耗时，且正确摘要不能代替研究收敛。不能把运行时间变长解释为压缩完全没工作，也不能据此宣称整体提速。

## 7. 后续修正优先级（仅建议，本轮未实施）

1. **执行存活性**：等待执行结果时监测内核退出，保存已收到输出并返回明确的执行失败。无需恢复一个任意科学时间预算，也不应静默重跑或无限等待。
2. **删重复产物清单**：固定目录保留；执行返回只给关键输出和当次新增/改变文件，历史快照留后台，报告不附每次执行的完整库存。不是再加共享索引。
3. **缩小实际交给专家的问题**：本轮初始消息仍是综合诊断套餐。物理/统计在首次发现重要不确定性或可区分的解释时应形成有内容的交接，让 Coordinator 决定是否值得继续；不是用更多“不要做”或编号项校验代替研究判断。示例：先回答形成与维持是否呈现不同解释及最关键证据缺口，而非预设完成全套 MLD/OHC/环流/预算。
4. **审核不吞掉作者完成事实**：将“作者报告已保存、审核中/失败”作为事实状态可见；未经审核不能假装已通过，但审核故障也不应让 Coordinator 永远不知道报告存在。对必要数值做针对性验证，与从头开展第二份完整研究区分开。

没有证据支持此时继续放宽预算能解决这些问题；本轮已经不靠固定调用预算终止。也不能将全部原因归于 Flash 能力——方法错误可能与模型有关，但内核等待缺陷、重复文件列表和交接滞后是代码可确认的独立问题。
