## 3. 新边界哪些有效、哪些仍有问题

### 已观察到的收益

1. 作者部分结果提前保存并通知 Coordinator，确实消除了“审核没完成就完全看不见作者结果”的情况。
2. 不再自动附加数万条历史文件链接。检查中的报告约 17 KB，而非旧次 4.8 MB；但报告头仍夹带完整审核修正问题，阅读上有重复和旧结论冲突。
3. API 超时/连接失败记录的 `counts_toward_round=false` 正确，不消耗有效额度。
4. 四个工作轮在快照中分别为 49、39、48、50 次有效调用，无单轮超过 60 的记录。报告已出现执行被关闭后的部分交接。尚无真实第 60 次收尾可供验证；不能将所有收尾都归因于 48 次阈值。
5. 代码均已返回（78 成功、27 失败），无长期 running 内核。最大单次返回代码执行约 178.8 秒；本轮未出现内核死亡、取消或超时事件，因而不能用本轮证明失活恢复已实测。

### 本轮暴露的具体缺陷

**A. 三种索引错误被误当成“同一错误修两次仍失败”。**

14:28:22 的 `index 71 / axis 0 / size 63`、14:29:11 的 `index 39 / axis 0 / size 30`、14:29:57 的 `index 49 / axis 1 / size 49` 来自不同代码步骤。用当前 `error_signature` 对原始 stderr 做只读复算，三者均得到：

`python-cell|IndexError|index # is out of bounds for axis # with size #`

签名既未保留用户代码操作位置，又抹掉轴/形状，因此第一次 20 次调用后的提前收尾并不能证明同一个 bug 已经两次修复失败。这是边界实现的误合并，不是模型单纯“不肯交付”。同时，27 个执行失败仍有 16 个 IndexError、5 个 ValueError；辅助函数存在并没有自动消除这些问题。

**B. 结果可见之后，旧审核与新工作轮没有形成清晰的生命周期边界。**

Coordinator 在 pending 时继续任务，旧审核/修正与新分析/审核后来并行；它们共用同一报告路径和审核 job key。报告及数据文件会更新，审核可能面对不同版本甚至共享内核状态。时间重叠、相同路径和 job key 是已观察事实；具体哪一次数值误判由覆盖/共享内核造成，尚不能直接确定。

**C. 审核既找到真问题，也制造自己的错误。**

审核指出 N² 符号、MLD 阈值插值负深度，以及预算 v1/v2 文件混用。后续作者/审核文字也承认部分旧诊断实际是文件单位理解错，例如审核撤回了给 v2 平流项再次乘 ρcp 后得到巨大数值的说法。说明审核有产物接触和纠错价值，但并非可信裁判；需要看同一份证据和单位。当前阶段不能把“审核说过有错/改好了”当作我已经独立确认所有数值。
